# ArxMint — Disaster Recovery Drill

**Version:** 1.0 | **Last updated:** 2026-02-28
**Network target:** Testnet (do the drill here first — do NOT drill on mainnet with real funds)

> **This is NOT the incident response runbook.**
> `docs/INCIDENT_RESPONSE.md` handles recovery of a *running* production system (LND restart, mint down, disk full).
> This document covers **full-stack restore from zero** — the scenario where the entire VPS is gone and you must rebuild from backups on a fresh machine. Run this drill before accepting real mainnet funds.

---

## Overview

**Purpose:** Validate that backup files are intact, that the restore procedure actually works, and that the stack is fully functional after a total VPS loss. Completing a successful drill is required before ArxMint accepts mainnet funds (per `MIGRATION_PLAN.md`).

**Recommended frequency:** Once before mainnet launch, then quarterly or before any major infrastructure upgrade.

**Expected duration:** ~2 hours on testnet (mainnet will take longer — LND channel sync can take 30+ min with more channels).

**What this drill simulates:** Total VPS loss. You provision a fresh machine, copy your backups to it, and restore everything from scratch. The drill passes only when all Phase 3 verification tests succeed.

**What the drill does NOT cover:**
- Partial failures (service crash, disk full) — see `docs/INCIDENT_RESPONSE.md`
- Fedimint multi-host guardian migration — see `docs/MIGRATION_PLAN.md`
- Data migration between versions — see `docs/MIGRATION_PLAN.md`

---

## Prerequisites

Before running the drill, confirm ALL of the following are in place on the *source* (production) machine:

- [ ] **Secondary environment available** — a second VPS, cloud VM, or local Docker Compose host. This MUST be a different machine from production. Never run the drill against your live stack.
- [ ] **`.env` backup** — offline copy on an encrypted USB drive or encrypted cloud storage (not version control). Must contain all required secrets: `CASHU_PRIVATE_KEY`, `POSTGRES_PASSWORD`, `GRAFANA_PASSWORD`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`.
- [ ] **LND `channel.backup`** — generated by `scripts/watch_channel_backup.sh`. Located at `/backups/lnd/channel.backup.latest`. Static channel backup enables recovery via `restorechanbackup`.
- [ ] **Postgres dump** — from most recent run of `scripts/backup_postgres.sh`. Located at `/backups/postgres/arxmint_TIMESTAMP.sql.gz`. Confirm it is less than 24 hours old.
- [ ] **Fedimint guardian volume exports** — Docker volume snapshots of `guardian-0-data`, `guardian-1-data`, `guardian-2-data`. See the export commands in Phase 2.
- [ ] **`docker-compose.yml` and `docker/` config directory** — keep a copy alongside your `.env` backup. The application image can be pulled from the registry; the config files are what you need.

## Phase 1: Backup Verification (no downtime, ~30 min)

Run this on the **production machine** before provisioning the drill environment. These checks confirm your backups are usable — no VPS downtime required.

### 1.1 Verify LND channel backup

```bash
# Check file exists and is non-zero bytes
ls -lh /backups/lnd/channel.backup.latest
# Expected: file size > 0, modified within the last 24 hours

# Check backup age (should be < 24h)
find /backups/lnd -name "channel.backup.latest" -mmin -1440
# Returns the file path if it exists and is recent; empty if older than 24h

# Confirm the watch script is running
ps aux | grep watch_channel_backup | grep -v grep
# If not running, restart it: nohup bash scripts/watch_channel_backup.sh /backups/lnd &
```

Record: backup age at drill time (minutes): ________

### 1.2 Verify Postgres backup

```bash
# Find the most recent backup
ls -lht /backups/postgres/ | head -5

# Dry-run restore to confirm the file is readable (no actual restore)
gunzip -c /backups/postgres/arxmint_TIMESTAMP.sql.gz | head -20
# Expected: PostgreSQL dump header, not empty or corrupted

# Alternative: use pg_restore --list on a .dump format file
# (backup_postgres.sh produces .sql.gz — the gunzip | head check above is sufficient)
```

Record the most recent backup filename: `arxmint_____________________`

### 1.3 Export Fedimint guardian volumes (pre-drill snapshot)

```bash
# Export all three guardian volumes to tar archives
# Run on production machine — containers can stay running during export
docker run --rm \
  -v guardian-0-data:/data:ro \
  -v /backups/fedimint:/backup \
  busybox tar czf /backup/guardian-0-data.tar.gz -C /data .

docker run --rm \
  -v guardian-1-data:/data:ro \
  -v /backups/fedimint:/backup \
  busybox tar czf /backup/guardian-1-data.tar.gz -C /data .

docker run --rm \
  -v guardian-2-data:/data:ro \
  -v /backups/fedimint:/backup \

# Verify archives are non-zero and listing works
ls -lh /backups/fedimint/
tar tzf /backups/fedimint/guardian-0-data.tar.gz | head -5
tar tzf /backups/fedimint/guardian-1-data.tar.gz | head -5
tar tzf /backups/fedimint/guardian-2-data.tar.gz | head -5
```

## Phase 2: Restore on Fresh Environment (~1 hour)

Run on the **fresh VPS or local Docker environment**. Do NOT run this on production.

### 2.0 Provision fresh environment

Option A — second VPS: provision Ubuntu 22.04 LTS, install Docker Engine + Docker Compose plugin. Copy backup files over via `scp` or USB.

Option B — local Docker Compose (recommended for testnet drill): use a separate directory or Docker context on your workstation. Ensure no port conflicts with any running stack.

```bash
# On the fresh machine: confirm Docker is available
docker --version
docker compose version

# Create backup directories
mkdir -p /backups/postgres /backups/lnd /backups/fedimint
```

### 2.1 Copy files to fresh environment

```bash
# Copy from production to drill machine (adjust paths as needed)
scp /backups/postgres/arxmint_TIMESTAMP.sql.gz  drill-host:/backups/postgres/
scp /backups/lnd/channel.backup.latest           drill-host:/backups/lnd/
scp /backups/fedimint/guardian-{0,1,2}-data.tar.gz drill-host:/backups/fedimint/

# Copy application stack
scp .env                                          drill-host:/app/
scp docker-compose.yml                            drill-host:/app/
scp -r docker/                                    drill-host:/app/docker/
```

### 2.2 Start database and proxy first

```bash
cd /app

# Start postgres and caddy first — no app logic yet
docker compose up -d postgres caddy

# Wait for postgres to be healthy
docker compose ps postgres
# Should show: healthy
```

### 2.3 Restore Postgres from backup

```bash
# Wait for postgres to finish initialization
sleep 10

# Restore from the backup dump
gunzip -c /backups/postgres/arxmint_TIMESTAMP.sql.gz \
  | docker exec -i sf-postgres psql -U arxmint arxmint

# Verify restore succeeded
docker exec sf-postgres psql -U arxmint -d arxmint \
  -c "SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY table_name;"
# Expected: list of ArxMint tables (Community, Merchant, Transaction, etc.)
```

### 2.4 Import Fedimint guardian volumes

```bash
# Create named volumes (they don't exist yet on fresh machine)
docker volume create guardian-0-data
docker volume create guardian-1-data
docker volume create guardian-2-data

# Import each volume from tar archive
docker run --rm \
  -v guardian-0-data:/data \
  -v /backups/fedimint:/backup:ro \
  busybox tar xzf /backup/guardian-0-data.tar.gz -C /data

docker run --rm \
  -v guardian-1-data:/data \
  -v /backups/fedimint:/backup:ro \
  busybox tar xzf /backup/guardian-1-data.tar.gz -C /data

docker run --rm \
  -v guardian-2-data:/data \
  -v /backups/fedimint:/backup:ro \
  busybox tar xzf /backup/guardian-2-data.tar.gz -C /data
```

### 2.5 Start remaining services

```bash
# Start LND first — it needs to sync before the mint can connect
docker compose up -d lnd

# Wait for LND to start (not yet synced — that happens in background)
sleep 30
docker compose logs --tail=20 lnd
# Expected: "Waiting for chain backend to finish sync" or "Opened wallet"

# Unlock LND wallet (enter wallet password when prompted)
docker exec -it sf-lnd lncli --network=testnet unlock

# Start Fedimint guardians
docker compose up -d fedimintd-0 fedimintd-1 fedimintd-2

# Monitor guardian startup — wait for consensus
docker compose logs -f fedimintd-0 &
# Look for: "consensus started" or "Guardian reached threshold"
# This can take 1-3 minutes
sleep 90

# Start Cashu mint, Aperture, and web app
docker compose up -d cashu-mint aperture web

# Verify all containers are running
docker compose ps
```

### 2.6 Restore LND channels via static channel backup

```bash
# Confirm LND is synced to chain before restoring channels
docker exec sf-lnd lncli --network=testnet getinfo | grep synced_to_chain
# Expected: "synced_to_chain": true
# If false, wait a few more minutes and recheck

# Perform static channel backup recovery
docker exec sf-lnd lncli --network=testnet restorechanbackup \
  --multi_file /root/.lnd/data/chain/bitcoin/testnet/channel.backup

# NOTE: This initiates a force-close of all channels on-chain.
# On testnet this is safe. On mainnet this broadcasts transactions — do this only after
# confirming the production LND node is permanently offline.

# Monitor channel recovery in LND logs
docker compose logs -f lnd
# Look for: "Inserting force closed channels" or channel sweep transactions
```

**Mainnet note:** On mainnet, LND data lives at `/root/.lnd/data/chain/bitcoin/mainnet/channel.backup`. The `restorechanbackup` command is the same; change `--network=testnet` to `--network=mainnet`. Force-closes result in on-chain transactions that take up to 2 weeks to settle (CSV timelock). Plan for this downtime.

## Phase 3: Verification Tests (~30 min)

All tests must pass for the drill to pass.

### 3.1 API health check

```bash
curl -s http://localhost:3000/api/health | jq .
```

**Pass criteria:** HTTP 200, `"status": "healthy"`, all sub-checks green (LND, cashu, postgres).

Result: PASS / FAIL — Notes: _______________________

### 3.2 LND channel list

```bash
docker exec sf-lnd lncli --network=testnet listchannels \
  | jq '[.channels[] | {active, capacity, local_balance, remote_balance, chan_id}]'
```

**Pass criteria:** At least one channel returned. Channels in recovery state (`active: false`) are expected immediately after restore — they will settle on-chain. The key check is that LND itself is running and the wallet is unlocked.

Result: PASS / FAIL — Channels found: _____, Active: _____

### 3.3 Fedimint quorum consensus

```bash
# Check logs for quorum/threshold messages
docker compose logs fedimintd-0 | grep -i "consensus\|threshold\|quorum" | tail -10
docker compose logs fedimintd-1 | grep -i "consensus\|threshold\|quorum" | tail -10
docker compose logs fedimintd-2 | grep -i "consensus\|threshold\|quorum" | tail -10
```

**Pass criteria:** At least one "consensus started" or "threshold reached" log line across the three guardians.

Result: PASS / FAIL — Notes: _______________________

### 3.4 Send a testnet Lightning payment

```bash
# Get a testnet invoice from a faucet (e.g., testnet.mymindful.app or similar)
# Then pay it from the restored LND node
docker exec sf-lnd lncli --network=testnet payinvoice <TESTNET_BOLT11_INVOICE>
```

**Pass criteria:** Payment settles with `payment_status: SUCCEEDED`.

Result: PASS / FAIL — Invoice: _______________________

### 3.5 Mint a Cashu ecash token

```bash
# Request a mint quote from the restored Cashu mint
curl -s http://localhost:3338/v1/mint/quote/bolt11 \
  -X POST -H "Content-Type: application/json" \
  -d '{"amount": 10, "unit": "sat"}' | jq .

# Pay the returned invoice on testnet, then mint the token
# (use the Cashu client library or the ArxMint wallet UI)
```

**Pass criteria:** Mint returns a valid `quote` object with a `payment_request` field. After paying, proofs are returned from `/v1/mint/bolt11`.

Result: PASS / FAIL — Notes: _______________________

### 3.6 Postgres data integrity

```bash
# Verify community and merchant counts match the pre-drill snapshot from Phase 1.4
docker exec sf-postgres psql -U arxmint -d arxmint \
  -c "SELECT 'communities' AS table_name, COUNT(*) FROM \"Community\" UNION ALL SELECT 'merchants', COUNT(*) FROM \"Merchant\";"
```

**Pass criteria:** Counts match pre-drill snapshot (communities = _____, merchants = _____).

Result: PASS / FAIL — Actual counts: communities = _____, merchants = _____

## Pass / Fail Criteria

The drill **passes** if all six Phase 3 tests pass.

The drill **fails** if any test fails. Document the failure, identify root cause, fix the backup or restore procedure, and re-run the drill from Phase 2.

**Do not proceed to mainnet** until you have a passing drill run with a log entry in the Drill Log below.
