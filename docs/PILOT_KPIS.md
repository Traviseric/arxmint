### BCE Health Score

The `computeHealthScore()` function in `lib/bce-metrics.ts` produces a composite 0-100 score.
At full-KPI achievement all five components reach maximum:

| Component | Weight | Full-marks threshold |
|-----------|--------|----------------------|
| Federation uptime | 25 pts | ≥ 99.5% |
| Payment success rate | 25 pts | ≥ 98% |
| Spend velocity | 20 pts | ≥ 5 tx/user/month |
| MAU | 20 pts | ≥ 300 |
| Active merchants | 10 pts | ≥ 30 |

A Health Score of **≥ 80 / 100** at the month-6 evaluation is the grant-continuation threshold.

### BCE Maturity Tier Targets

The `classifyMaturityTier()` function in `lib/bce-metrics.ts` defines thresholds:

| Tier | Merchant threshold | MAU threshold | Expected at |
|------|--------------------|---------------|-------------|
| Nascent | 0–9 | 0–49 | Pre-launch |
| Emerging | 10–29 | 50–199 | Q1–Q2 |
| Growing | ≥ 30 | ≥ 200 | Q3 pilot target |
| Established | ≥ 100 | ≥ 1,000 | Post-pilot expansion |
| Thriving | ≥ 100 | ≥ 1,000 (both) | Long-term goal |

**Pilot success gate:** reach **Growing** tier by month 6 (30 merchants + 300 MAU individually both meet that threshold).

## 3. Measurement Methodology

Every KPI has a documented data source. All queries run against the Postgres database via Prisma.

### 3.1 Merchant Count

- **Table:** `Merchant` (Prisma schema)
- **Query:** `prisma.merchant.count()` for total; `prisma.merchant.count({ where: { status: 'active' } })` for active
- **Mapped to:** `BCEMetrics.merchantCount` and `BCEMetrics.merchantsActive`
- **Cadence:** Snapshot at report generation time

### 3.2 Monthly Active Users (MAU)

- **Definition:** Distinct users who completed at least one `Transaction` in the rolling 30-day window
- **Tables:** `Transaction`, optionally `Session`
- **Query:**
  ```sql
  SELECT COUNT(DISTINCT "userId")
  FROM "Transaction"
  WHERE "createdAt" >= NOW() - INTERVAL '30 days'
    AND "status" = 'completed';
  ```
- **Mapped to:** `BCEMetrics.mau`

### 3.3 Repeat-Spend Percentage (User Retention)

- **Definition:** Percentage of MAU who completed ≥ 2 transactions in the reporting period
- **Query:**
  ```sql
  WITH user_counts AS (
    SELECT "userId", COUNT(*) AS tx_count
    FROM "Transaction"
    WHERE "createdAt" >= NOW() - INTERVAL '30 days'
      AND "status" = 'completed'
    GROUP BY "userId"
  )
  SELECT
    COUNT(CASE WHEN tx_count >= 2 THEN 1 END) * 100.0 / COUNT(*) AS repeat_spend_pct
  FROM user_counts;
  ```
- **Target:** ≥ 40% of MAU are repeat spenders by month 6
- **Not currently tracked in `LONGMONT_KPI_TARGETS`** — add as supplemental metric in grant reports

### 3.4 Transaction Volume

- **Table:** `Transaction`
- **Column:** `Transaction.amount` (sats)
- **Query:** `SUM(amount)` filtered by `status = 'completed'` and date range
- **Reported as:** total sats per period and rolling 30-day volume
- **Mapped to:** `BCEMetrics.ecashCirculation` (outstanding ecash) and raw volume in grant reports

### 3.5 Payment Success Rate

- **Formula:** `successfulTransactions30d / totalTransactions30d`
- **Tables:** `Transaction`
- **Query:**
  ```sql
  SELECT
    COUNT(CASE WHEN status = 'completed' THEN 1 END) AS successful,
    COUNT(*) AS total,
    COUNT(CASE WHEN status = 'completed' THEN 1 END)::float / COUNT(*) AS success_rate
  FROM "Transaction"
  WHERE "createdAt" >= NOW() - INTERVAL '30 days';
  ```
- **Mapped to:** `BCEMetrics.paymentSuccessRate` via `computeBCEMetrics()` in `lib/bce-metrics.ts`

### 3.6 Federation / Mint Uptime

- **Formula:** `uptimeMinutes30d / (30 × 24 × 60)`
- **Source:** Prometheus metric `up{job="fedimint"}` or `up{job="nutshell"}`, scraped every 30 seconds
- **Grafana:** `docker/grafana/dashboards/` — federation uptime panel
- **Mapped to:** `BCEMetrics.uptime` via `computeBCEMetrics()`

### 3.7 Spend Velocity

- **Formula:** `totalTransactions30d / mau`
- **Tables:** `Transaction` (completed, rolling 30d), distinct user count
- **Mapped to:** `BCEMetrics.spendVelocity` via `computeBCEMetrics()`
- **Target:** ≥ 2.0 tx/user/month

### 3.8 BCE Health Score

- **Function:** `computeHealthScore()` in `lib/bce-metrics.ts`
- **Inputs:** `BCEMetricsInput` struct (all DB-sourced fields above)
- **Output:** 0–100 composite score
- **Used in:** dashboard at `app/dashboard/page.tsx`, grant progress reports via `generateProgressReport()`

## 4. Success / Failure Thresholds

For each primary KPI, three performance bands are defined:

| KPI | Green (≥ 90% of target) | Yellow (50–89%) | Red (< 50%) |
|-----|------------------------|-----------------|-------------|
| Merchants onboarded (target: 30) | ≥ 27 | 15–26 | < 15 |
| MAU (target: 300) | ≥ 270 | 150–269 | < 150 |
| Payment success rate (target: 98%) | ≥ 88.2% | 49–88.1% | < 49% |
| Federation uptime (target: 99.5%) | ≥ 89.6% | 49.75–89.5% | < 49.75% |
| Spend velocity (target: 2 tx/user/mo) | ≥ 1.8 | 1.0–1.79 | < 1.0 |
| BCE Health Score (target: 80) | ≥ 72 | 40–71 | < 40 |

### Minimum Viable Success for Grant Continuation

For a grant reporting period to be considered "on track" and eligible for the next tranche:

- **Payment success rate ≥ 93%** at any monthly checkpoint (hard floor — below this indicates a production defect)
- **Uptime ≥ 97.5%** at any monthly checkpoint
- **Merchant count and MAU must be proportionally on-track** — evaluated as `actual / target >= reportMonth / 6` (linear ramp check in `generateProgressReport()` in `lib/bce-metrics.ts`)
- **No confirmed fund loss** in any period (automatic grant pause trigger regardless of other KPIs)

## 5. Escalation Criteria

### 5.1 Pause Triggers (Stop Pilot Operations)

Any of the following triggers an immediate operational pause pending investigation:

| Trigger | Threshold | Action |
|---------|-----------|--------|
| Payment success rate crash | < 90% in any 24-hour window | Pause merchant-facing payments; investigate LND or mint |
| Federation guardian offline | Quorum at risk (< N/M guardians) | Alert guardian council; attempt restart within 1 hour |
| LND channel failure | All outbound channels closed | Emergency channel reopen from reserve; pause new invoices |
| Confirmed fund loss | Any amount, any user | Immediate pilot pause; incident report within 24 hours |
| Security incident (auth bypass, token theft) | Any confirmed incident | Pause all API endpoints; rotate all secrets |
| Uptime < 95% over 7-day window | Rolling 7-day uptime below threshold | Alert guardian council; escalate to infrastructure review |

Pause procedure is documented in `docs/INCIDENT_RESPONSE.md`.

### 5.2 Proceed-to-Mainnet Gate

All of the following must be true before authorizing mainnet migration:

1. **All Q4 KPIs met at Green level** (≥ 90% of all targets)
2. **Zero confirmed fund losses** over the entire pilot
3. **Guardian distribution plan executed** — guardians distributed across ≥ 3 independent operators / locations (from `docs/TRUST_STATEMENT.md` requirements)
4. **Value caps in place** — pilot value caps (`lib/` configuration) must be explicitly lifted by guardian vote before mainnet
5. **Replication playbook reviewed** — at least one external community has reviewed the playbook (`lib/replication-playbook.ts`)
6. **Security audit complete** — no P0/P1 findings open

### 5.3 Hard Stop (Terminate Pilot)

Pilot is permanently terminated (not just paused) if:

- **Any confirmed user fund loss**, even if within value caps
- **Fraudulent merchant activity** detected and unresolvable
- **Regulatory intervention** from local / federal authorities
- **Two consecutive grant reporting periods** in Red status with no recovery trend

## 6. Grant Reporting Schedule

### 6.1 Reporting Cadence

Per OpenSats requirements, the schedule is generated by `generateReportSchedule(6, startDate)` in `lib/bce-metrics.ts`:

| Report | Period | Cadence | Due Date |
|--------|--------|---------|----------|
| Report #1 | Month 1 | Monthly | Start + 1 month |
| Report #2 | Month 2 | Monthly | Start + 2 months |
| Report #3 | Month 3 | Monthly | Start + 3 months |
| Report #4 | Q2 (Month 6) | Quarterly | Start + 6 months |
| Final Report | Month 6 | Quarterly | Start + 6 months |

> Note: For a 6-month pilot the quarterly report and final report coincide at month 6.
> Evaluation-phase reporting (months 7–9) is submitted as expansion planning documents, not grant reports.

### 6.2 Report Contents (per `exportReportMarkdown()`)

Each report must include:

- KPI progress table: target vs actual for all 5 primary KPIs
- BCE Health Score and maturity tier
- Milestone status (from `generatePilotTimeline()` phases)
- Progress narrative, challenges, and next-period goals
- Budget expenditure to date

Use `generateProgressReport()` → `exportReportMarkdown()` in `lib/bce-metrics.ts` to auto-generate the structured report, then add narrative context.

### 6.3 Public Transparency

- **Monthly public writeups:** Brief community updates on the ArxMint project site
- **Quarterly public posts:** Detailed technical writeups including anonymized KPI data
- **KPI dashboard link:** Grafana public dashboard (read-only) at `docker/grafana/dashboards/` — link to be published in all grant reports once live on production server

### 6.4 Multi-Funder Reporting

| Funder | Report format | Cadence | KPI emphasis |
|--------|--------------|---------|--------------|
| OpenSats | `generateProgressReport()` Markdown | Monthly (M1–M3), Quarterly (M4–M6) | All KPIs; payment success rate prominent |
| HRF | Narrative + KPI table | Quarterly | Human rights / financial privacy angle; MAU and merchant count |
| Spiral | Technical progress | Quarterly | Lightning infrastructure; uptime and payment success |

Use `generateFBCEApplication()` and `generateOpenSatsApplication()` in `lib/grant-templates.ts` to produce application drafts; update `kpiTargets` field with values from `LONGMONT_KPI_TARGETS`.

## Appendix: KPI Data Flow

```
Postgres DB (Transaction, Merchant tables)
        ↓
BCEMetricsInput struct (raw counts, sums)
        ↓
computeBCEMetrics() — lib/bce-metrics.ts
        ↓
BCEMetrics snapshot (health score, tier, velocity, etc.)
        ↓
evaluatePilotKPIs() — lib/pilot-deployment.ts
        ↓ ↓
KPIEvaluation[]    generateProgressReport()
(dashboard)        (grant reports)
```

All KPI data originates in the Postgres database and flows through `computeBCEMetrics()` before reaching the dashboard or grant reports. This single source-of-truth prevents discrepancies between what users see in the dashboard and what is reported to grantors.
